# База данных Asyq League

## Что нужно сделать один раз

Две вещи можно сделать только из дашборда проекта — у CLI без токена доступа их нет.

### 1. Включить гостевой вход

**Authentication → Sign In / Providers → Anonymous Sign-Ins → включить.**

Без этого игра работает, но полностью локально: прогресс не уходит в облако,
а на главной висит плашка «Облако выключено».

### 2. Применить миграции

**Вариант А — дашборд, одним куском (быстрее всего).**
SQL Editor → New query → вставить целиком [`apply-all.sql`](apply-all.sql) → Run.

Это склейка всех миграций. Файл идемпотентный: если что-то пойдёт не так,
его можно запустить ещё раз. Пересобирается из миграций командой
`node scripts/build-apply-all.mjs`.

Если хочется применять по частям — те же файлы лежат в `migrations/`:

```
20260930000100_schema.sql        таблицы и индексы
20260930000200_rls.sql           политики доступа и права ролей
20260930000300_functions.sql     триггеры и серверные функции
20260930000400_universities.sql  справочник вузов
```

**Вариант Б — CLI:**

```bash
npx supabase login
npx supabase link --project-ref gosmzpcdrjwldiyodpdf
npx supabase db push
```

### 3. Засеять вузы и тестовый аккаунт

Нужен ключ `service_role` (Project Settings → API). В браузер он не попадает
и в репозиторий не коммитится.

```bash
SUPABASE_SERVICE_ROLE_KEY=... node scripts/seed-supabase.mjs
```

Скрипт создаёт аккаунт проверяющего и немного прогресса, чтобы было что посмотреть:

```
почта:  reviewer@asyqleague.kz
пароль: AsyqLeague2026!
```

### 4. Google-вход (необязательно)

**Authentication → Providers → Google** — указать Client ID и Secret,
а в Google Cloud Console добавить redirect URI
`https://<project-ref>.supabase.co/auth/v1/callback`.
Без этого кнопка «Через Google» покажет ошибку, остальное работает.

## Как устроен доступ

Правило одно: **писать можно только своё**. Публично читаются лишь те таблицы,
без которых не работают таблицы лидеров.

| Таблица | Чтение | Запись |
|---|---|---|
| `universities` | все | нет (сид) |
| `profiles` | все (нужно лидербордам) | только свой |
| `progress` | только свой | только свой |
| `results` | только свои | только свои |
| `daily_results` | все (лидерборд) | только вставка своего; **UPDATE запрещён** |
| `custom_levels` | все | автор |
| `matches` | только участники | создатель / участники |
| `moves` | участники матча | только свой ход и только когда очередь твоя; UPDATE и DELETE запрещены |
| `purchases` | только свои | только свои |
| `tournaments` | все | владелец |

Две вещи вынесены на сервер, потому что клиенту их доверять нельзя:

- `save_progress()` — рекорд **только улучшается**: звёзды берутся по максимуму,
  броски по минимуму;
- `save_daily_result()` — **одна зачётная попытка в день**: повторная запись
  молча отбрасывается, и функция возвращает `false`.

## Проверка SQL без Supabase

```bash
./scripts/test-supabase-sql.sh
```

Скрипт поднимает временный локальный Postgres, эмулирует схему `auth`
(таблица `auth.users`, функция `auth.uid()`, роли `anon`/`authenticated`
с теми же грантами, что выдаёт Supabase), применяет все миграции и проверяет:

- триггер создаёт профиль вместе с пользователем;
- рекорд в `save_progress` улучшается и не ухудшается;
- вторая попытка в ежедневном испытании отвергается;
- один игрок не может ни прочитать, ни записать данные другого;
- таблица лидеров собирается и сортируется правильно;
- RLS включён на всех таблицах.

Этот прогон нашёл реальную ошибку: функции падали без гранта
`usage on schema auth` — в Supabase он есть по умолчанию, в чистом Postgres нет.
